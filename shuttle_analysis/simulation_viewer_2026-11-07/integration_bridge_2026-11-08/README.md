# v5 → 개인 경로 추천 연동 명세

기준은 보존된 `city_bus_model_2026-11-08/prepared.json.gz`의 `campus_stop_corridors_20261108`입니다. 이 폴더는 연동 자료만 생성합니다. 원래 모델·결과·`app/`와 현재 공개 사이트는 변경하지 않습니다. 앱의 관측 ETA·통과 이력·구간속도 근거 우선순위와 보행망은 앱 소유자가 유지합니다.

## 제공 파일과 검산

- `bridge.py`: 표준 라이브러리만 사용하는 거리·경계 분할·가감속·구간시간 조회·조건부 FIFO 예측 함수입니다.
- `route_time_inputs.json`: 12개 노선(셔틀4·시내8), 인접354구간의 보존 소요시간·거리·교내/교외 길이·정차 규칙·정류장 인덱스·예시 배차 입력입니다. 약183KB이며 원래 이동 입자·수업 명단은 없습니다.
- `fixtures.json`: 실제 경계/교내 보완/교외 구간, 거리0의 정차, 복수 정차, 만차·하차·공동노선·호환 FIFO의 검산 입력입니다.
- `verify_fixtures.py`: `python -S verify_fixtures.py`로 외부 패키지 없이 실행합니다.
- `export_and_verify.py`: 보존 v5에서 추출하는 개발용 도구입니다. 기존 프로젝트 Python 의존성을 이용하며 앱 배포에 넣을 필요가 없습니다.
- `verification.json`: 354구간의 가감속 시간·경계별 위상·거리와 보존 v5가 일치합니다. 시간 오차 최댓값0초, 큐 예측5사례는 원래 참조 함수와 일치합니다. 현실 정확도 검증과 구분합니다.
- `source_manifest.json`: 추출 시각, 파일별 SHA-256, 함수·클래스 시작 행, 보존 입력과 bridge/JSON 해시를 기록합니다. 비교한 앱 파일은 `app_reference_snapshot/`에 읽은 바이트 그대로 복사했습니다. 현재 앱의 계속되는 수정과 이 스냅샷을 구분합니다.

## 가장 중요한 정차·시계 규칙

1. `kinematic_profile()`은 인접 도로 구간을 약5m 이하 셀로 나누고 가속·감속1m/s², 각 셀 최고40/65km/h, 각 정류장 속도0을 적용합니다. 원래 도형의 한 변을 최소2개 셀로 나누는 규칙도 같습니다.
2. **각 cut의 끝에15초를 더하며 최종 목적 정류장의15초도 포함합니다.** 거리0이어도 cut 하나면15초입니다. 두 cut이면 정차 합계30초입니다. 최초 출발점에 별도15초를 먼저 더하지 않습니다.
3. v5의 차량 이벤트·`offsets_seconds`는 그 도착 정류장의 정차까지 포함한 서비스 시각입니다. 승하차도 이 서비스 이벤트에서 처리합니다. `ride_seconds()`는 이 오프셋 차이이므로 목적 정류장의 정차를 포함합니다. 오프셋이나 다음 출발시계에 다시15초를 더하지 않습니다.
4. 시내 구간은 `max(가감속·정차 곡선 시간, 도로거리/(보존 구간속도/3.6))`입니다. 관측속도 항에15초를 추가하지 않습니다. **이 최댓값 전체에서 무조건15초를 빼서 실제 주행시간으로 해석할 수 없습니다.** 속도 스냅샷의 정차 포함 정의가 미확인이며 뷰어는 더 긴 전체 시간에 곡선의 이동·정차 위상을 함께 늘립니다.
5. 앱이 ‘정차 전 도착’ 정의를 선택하면 별도 규칙과 검산이 필요합니다. 도착/출발 관측의 끝점 정의를 먼저 맞추세요. 실제 완료 관측이나 동일 차량 ETA 차이를 시나리오 하한으로 강제 보정하지 않습니다.
6. 승객의 승차 준비20초는 차량 정차15초와 별개의 처리입니다. 이미 같은 승차지에서 준비를 마친 경우 재가산하지 않습니다. 재선택의 같은 승차지·접근0 조건은 추가 준비0, 걸어서 옮기면 다시20초입니다.

## bridge 함수 계약

| 함수 | 입력 | 출력·단위 |
|---|---|---|
| `distance_m(a,b)` | `[위도,경도]` 두 점 | v5와 같은 근거리 거리, m |
| `zones(p,q,ring,force_campus=False)` | 닫힌 `[위도,경도]` 경계, 한 도로 변 | `(길이m,상한km/h)` 목록 |
| `kinematic_profile(points,cuts,ring,force_campus=False,accel=1,dwell=15)` | 마지막 점을 포함하는 오름차순 정류장 점 인덱스 | `t`초, `d`m, `v`m/s, `cap`km/h, `duration`초 |
| `city_segment_seconds(profile,saved_speed_kmh)` | 곡선·유효 속도 스냅샷 또는None | v5의 조건부 구간 총시간, 초 |
| `ride_seconds(inputs,rid,i,j)` | 배포 JSON, 보존0기반 인덱스 `i<j` | 보존 서비스 이벤트 간 초 |
| `find_stop_indices(route,stop_id,source_seq=None)` | 물리 ID·선택적 원문 순번 | 일치하는 **모든** 인덱스. 반복 방문을 자동 병합하지 않음 |
| `first_boardable(rows,vehicles,ready,now,stage,weight,waiting)` | 아래의 명시된 시간·현재 상태 | `(출발초,vehicle_index,board_index,선택stage)` 또는None |

`rows`는 `(서비스시각초, vehicles 배열 인덱스, 해당 노선 보존 승차 인덱스)`로 정렬한 목록입니다. JSON의 배열도 받습니다. `vehicles` 항목은 `rid`, 숫자 `cap`, 처리 완료 순번 `last_stop`, `onboard=[(하차인덱스,{'w':가중치}),...]`입니다. `stage`는 `rid/board/alight`이며 정문 공동노선은 같은 구조들의 `pool`을 갖습니다. 앞선 대기 흐름은 `{'w':가중치,'stage':현재단계번호,'stages':[stage,...]}` 목록입니다. 개인 조회는 보통 `weight=1`입니다. 큰 가중치를 주면 해당 가중치 전체의 승차가 끝나는 시각을 반환합니다.

예측은 현재 차내에서 이 승차지까지 내리지 않는 가중치와 현재 줄만 사용합니다. 호환되지 않는 노선 대기는 여석을 소비하지 않습니다. 앞선 줄은 조회 승객이 오기 전에 출발하는 차량으로 먼저 빠질 수 있습니다. 미래 새 유입·아직 일어나지 않은 상류 승차·외부 배경 승객은 예측하지 않습니다. 함수는 입력을 변경하지 않습니다. 구현은 원래 `city_capacity_model.first_boardable()`의 목록 참조 분기입니다. 대규모 원래 시뮬레이터는 같은 결과의 `QueueView/indexed_boardable` 최적화를 사용합니다.

**실제 여석이 없으면 이 함수에50/24를 확정값으로 채우지 않습니다.** JSON의 정원은 사용자/제조사 시나리오이며 차량 등록정원이 아닙니다. 실제 관측이나 명시적으로 선택한 시나리오가 있을 때 조건부 결과로 표시하세요.

## JSON과 인덱스·시간 기준

- `routes[rid].segments[k]`: `k→k+1`의 `model_seconds`, `kinematic_seconds`, 거리·교내/교외 길이·보존 속도·도착 정차 규칙입니다.
- `offsets_seconds`는0기반 보존 정류장 배열의 누적 시간입니다. 왕복·순환은 같은 물리 정류장이 여러 번 등장합니다. 셔틀 순환은 첫 `boarding_node_count`개가 승차 노드이며, 후속 확장 정류장은 이전 승객의 하차를 표현합니다. 모델의 모든 확장 정류장을 새 승차 노드로 만들지 않습니다.
- 앱의0기반 인덱스와 바로 대응한다고 가정하지 않습니다. `id`·`source_seq`·반복 방문을 함께 대조합니다. 일치하는 정방향 구간이 없으면 기존 앱 근거로 돌아가며0초로 계산하지 않습니다.
- 셔틀 `anchor_dispatches_seconds`는 해당 `anchor_index`의 기준/피크 시각입니다. `t0=anchor_departure-offsets[anchor]`입니다. 고유 실차 대수나 기사 회차 계획이 아닙니다.
- 시내 `weekday_plan`은 기점 첫차·막차·간격으로 재구성하는 가정입니다. `t0=origin_departure+origin_to_modeled_first_seconds-offsets[anchor]`입니다. 초는 KST 서비스일 자정 기준이며 Unix epoch가 아닙니다. 주말 계획이 아닙니다.
- 5515·5528·6515는 정문→입구역5정류장만입니다. 그 밖의 구간을 이 JSON으로 추정하지 않습니다. 기점→정문 시차는 추정이고 상류 승객은 포함하지 않습니다.
- 시내 `campus_stop_corridor_40=true`인116구간은 경계 밖 도로도40입니다. 셔틀은 보존 v3 경계 곡선을 그대로 가진 `frozen_v3_polygon`입니다. 이 자료를 만들면서 셔틀의 경계 분류를 소급 변경하지 않았습니다. 지도상 소속·법정 제한속도의 실측 검증과 구분하세요.

```python
import json
from pathlib import Path
from bridge import ride_seconds, find_stop_indices

data=json.loads(Path('route_time_inputs.json').read_text(encoding='utf-8'))
route=data['routes']['100100251']
assert len(find_stop_indices(route,'120000029')) >= 1
seconds=ride_seconds(data,'100100251',0,1)
print(seconds)  # 보존 v5 조건부 fallback. 관측 ETA라고 표시하지 않음.
```

## 후보 생성·선택의 실제 범위

v5 최초 경로는 이미 고정된 입자를 재사용합니다. `model_snapshot/engine/simulate_stop_inflow.build_candidates()` → 보존 `model_snapshot/app/routing.Planner.patterns()`가 원래 후보 생성 계약이며, 최신40/65 조건에서 최초 선택 전체를 다시 탐색한 알고리즘은 아닙니다.

보존 Planner는 직접 보행과 직행/최대1회 환승을 다룹니다. 승차 후보는 직선800m 안 최대5개를 검사하고 실제 보행1300m 이하 중 노선당3개를 남깁니다. 하차는 목적지 직선650m 안·보행1000m 이하 중2개입니다. 환승은 같은 물리 정류장 또는 셔틀 관련 직선180m 안 노선당2개 후보와 실제 보행300m 제한을 사용하며, 첫 승차 후 최대16개 하차 위치를 확인합니다. 반복 노선을 조용히 감싸지 않습니다.

`rough`는 접근·이탈·환승 보행과 옛18km/h+도착 정류장당15초, 셔틀90초/시내 간격 절반을 합칩니다. 첫 노선·승차 횟수 그룹당3개, 전체32개로 줄입니다. `prepare_adaptive.py`는 이 목록에서 서로 다른 첫 노선의 최대8개를 추가 후보로 택하고 별도 정문5노선 후보를 더합니다. 시내 줄의 새 후보는 직접 보행과 준비된 같은 승차지 후보 최대12개입니다. 전역 최단/최단 도착 보장은 없습니다.

원래 초기 선택에는 건물 이탈60/180/480초 삼각분포, 보행 속도0.9/1.2/1.5m/s, 환승당120초 선택 비용, Gumbel90초와 시드20261106이 사용됐습니다. 이는 코호트 취향/수요 가정이며 개인 ETA나 실측 계수로 이식하지 않습니다. v5 경로 재판단은 현재 이후의 남은 ETA를 비교하고120초 개선·180초 유지·최대2회입니다. 이미 소비한 시간은 다시 더하지 않습니다.

임의 GPS·목적지의 후보는 앱의 현행 보행망/확인 출입구와 Planner에서 생성하세요. 앱에서 요청 시각의 대기·차내시간 전파를 평가한 뒤 후보를 줄이는 개선은 별도 새 구현입니다. v5를 가져오면 rough 사전 절단 문제가 해결됐다고 표현하지 않습니다.

## 앱 대조 스냅샷과 이식 지점

| 앱 파일 | 확인한 현행 동작 | 연결 범위 |
|---|---|---|
| `routing.py` | 보존 탐색과 유사한 후보+정문 보호, rough40개·그룹3개. `ride_seconds()`는 rough에서 현재 시각 사용 | 후보 생성·실제 보행은 유지. 요청 시각 전파 뒤 후보 축소는 앱에서 개선. live 관측16쌍 상한 유지 |
| `travel_time.py` | 같은 방향 완료 통과 이력 n≥5·2일이면 먼저 사용. 셔틀 fallback은 거리/5+중간 정류장15초. 시내는 신선한 속도→과거 속도→18 가정 | v5는 **fallback 구간시간**에 연결. 실제 완료 관측의 끝점 정의와 근거 보존 |
| `routing.py`의 live 처리 | 같은 차량·신선한 양끝 ETA 차이가 있으면 ride 정보를 바꿀 수 있음 | 제공기관 예측 차이와 실제 완료시간을 구분. 모델 하한으로 강제 자르지 않음 |
| `gate_service.py` | 확인된 첫 ETA 또는 독립 균등 잔여대기의 최솟값/노선확률 | 미래 기대값을 확정 출발로 바꾸지 않음. 현재 줄/차량 여석이 명시된 경우에만 조건부 FIFO 적용 |
| `automatic_queue.py` |5분 유입을 현행 config.step_seconds=15초로 분배(함수 기본값30초와 구분),20초 준비, OD 비례 하차·reserve·수요 배율, 공유 셔틀 차량 | 구간 오프셋은 같은 fallback으로 맞출 수 있음. 이 모형과 v5 개별 상태/재선택은 다르므로 전체 교체 전 별도 검산 |
| `prepare_auto_queue.py`, `ShuttleTimetable` | 앱에서 거리/5+정차로 오프셋을 만드는 지점이 있음 | ride fallback·차량 진행·역순환 도착 오프셋의 정차 기준을 함께 통일 |

차내시간은 준비→첫 승차 가능 시각→차내→환승 보행→다음 준비/대기를 순서대로 전파합니다. 최신 관측·완료 이력·구간속도와 모형 fallback의 출처를 별도 보존합니다. 코호트 평균 절감량을 개인 ETA에서 빼거나 시간당 재차합을 실제 차량 여석으로 변환하지 않습니다. 앱 배포·활성화와 그 결과 검증은 앱 소유 에이전트가 담당합니다.
