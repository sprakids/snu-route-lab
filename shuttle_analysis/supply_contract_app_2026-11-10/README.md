# 행정관–서울대입구역 셔틀 공급 계약 개선

사용자의 반복 경험과 이용자 공통 증언을 `field_observations_2026-11-10/peak_pair_operation_evidence.json`에 기록하고 시뮬레이션 담당 에이전트에 전달했다. 이는 반복 운영에 대한 정성 근거다. 정확한 배차간격·피크 시작과 종료·매번 두 대 운행 여부·도착시각의 독립 실측으로 만들지 않았다.

## 계산 의미

- 낮 시간의 행정관–설입 차량 정원은 44명으로 수정할 수 있다. 21시 이후 60명은 별도 확인되지 않은 종전 야간 서비스 가정을 유지하는 계약이다.
- `capacity_periods: [{start_second: 75600, capacity: 60}]`는 차량의 원래 터미널 출발 시각으로 판정한다. 도중에 21시를 넘거나 실시간 시계 보정이 일어나도 같은 차량의 정원이 바뀌지 않는다.
- `dispatch_batches: [{start_second: 54000, end_second: 68400, vehicles: 2}]`는 시작 포함·종료 제외 구간이다. 15~19시는 검토용 적용 창이며 실측으로 확정한 피크 구간이 아니다. 명목 출발 시각마다 개별 차량을 두 대 생성하고 차내량과 정원은 각각 유지한다.
- 두 대를 한 대 88명 또는 90초 균등 배차로 치환하지 않는다. 다른 시각·다른 노선·다른 차량의 공급은 바꾸지 않는다.
- 야간 41915는 주간 41841의 공동 프로필에서 해당 차량을 선택한다. 별도 수요나 차량을 복제하지 않고 선택 차량의 정원을 응답한다.
- 원래 scalar60 seed의 의미와 해시는 유지한다. 구계약에서 승인된 44명 단독/2대 묶음 두 계약으로만 전환을 허용한다. 토폴로지·다른 노선 정원·기간 경계의 임의 변경은 거부하며, 정원 수정 후 60명 일괄 계약으로 조용히 복귀하지 않는다.
- 시간표 간격은 보존한다. regular 15~19시는 기존 4분이며, 시뮬레이터의 별도 peak 3분 공급 시나리오를 앱의 실측 배차로 취급하지 않는다.

## 검증과 보존

새 공급·21시 경계·예비 여석·별도 차량 FIFO·야간 alias·해시 이행·동시 요청 고정·준비 전 취소 거부와 기존 길찾기/운행을 포함해 83개 테스트를 통과했다. 상세는 `verification.json`이다. 원본은 `before_apply`에 보관했고 적용 패치는 `app_supply.patch`이다.

APP seed·원래 shuttle_clock·86개 보호 데이터/화면 자산의 변경이 없음을 확인했다. 개인용 `adaptive.py`와 화면은 수정하지 않았다. 준비 스크립트는 검산한 SOURCE에 명시된 공급만 복사하며 `prepare_auto_queue.build()`도 같은 최신 어댑터로 연결된다. 옛 `build_legacy()`는 변경하지 않았다.

현재 시뮬레이터의 도착·승차·출발 사건은 실측의 줄 대기 189초와 승차 후 30초를 분리 재현하지 못한다. 회차 공급 수정 검증과 예측 정확도 검증은 별개다. 실측은 15:23 합류, 본인 포함 외부 줄67명, 이후 대략15:24 이후 두 차량 도착, 그 두 번째 차량에 탑승한 한 사례로 유지한다. 순수 줄 대기189초 전체를 배차 대기 또는 승차 처리 시간 하나로 맞추지 않는다.

## 운영 상태

로컬 구현과 검증은 완료했지만 Vercel 팀 권한 및 저장 CLI 로그인이 만료되어 실제 배포는 진행하지 못했다. `deploy --dry`에서 중단했으며 소스 업로드·도메인 변경·latest 공개 전환은 없었다. 공개 앱과 실험실 feed는 확인 시점 모델261110150729를 유지한다. 에이전트에도 새 reader가 배포되기 전 feed 공개를 보류하도록 전달했다.

다음 순서는 APP reader 배포 → `/api/queue-model`의 `vehicle_supply_contract` 확인 → 검산된 새 모델을 실험실 담당자가 명시적으로 발행 → 모델·payload 해시·단일 요청 계산 시계 확인이다. 새로운 모델의 실제 정확도가 입증됐다는 뜻은 아니다.
