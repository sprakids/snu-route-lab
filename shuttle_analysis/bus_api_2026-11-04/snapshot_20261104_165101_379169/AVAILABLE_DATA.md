# 현재 위치·배차간격·도착예정시간 조회 확인

**조회시각: 2026-11-04 16:51:01 KST.** 위치 OpenAPI는 보관된 키로 호출했고, 노선 기본정보와 정류소별 도착예정은 서울시 공식 모바일 버스정보 웹 조회 인터페이스로 받았다. 서로 다른 조회 경로임을 구분한다.

| 정보 | 실제 확보 필드 | 지도에서의 용도 |
|---|---|---|
| 차량별 최근 위치 | `gpsX`, `gpsY`, `vehId`, `dataTm` | 차량 마커와 데이터 제공시각 표시 |
| 등록 배차간격 | `term` | 노선 기본정보와 예상 대기시간의 보조정보 |
| 특정 정류소의 다음 두 도착예정 | `arrmsg1/2`, 모바일 응답의 `traTime1/2` | 해당 정류소에서 탈 버스와 기다릴 시간 비교 |
| 운행 구간·최종 정류소 | `sectOrd`, `lastStnId` | 순환노선의 정차 순번과 함께 방향 판별 |
| 첫차·막차 | `firstBusTm`, `lastBusTm` | 제공된 노선 운행시간 안내 |
| 차량 혼잡도·만차 표시 | `congetion`, `isFullFlag` | 제공되는 차량에 한해 탑승 가능성 판단 보조 |

최종 정류소 ID만으로 정차 중이라고 판단하지 않는다. 같은 정류소가 순환노선에 반복되므로 노선 ID·정류소 ID·노선 내 정차 순번을 함께 유지한다.

## 등록 배차간격

| 노선 | 이번 노선정보 응답의 `term` | 위치 반환 차량 수 |
|---|---:|---:|
| 5511 | 7분 | 11 |
| 5513 | 9분 | 6 |
| 5516 | 9분 | 13 |
| 관악02-1 | 5분 | 9 |
| 관악02-2 | 10분 | 4 |
| 합계 | — | 43 |

서울시 공식 사이트의 `mobile_commbus.js`는 `term` 값을 ‘배차간격’과 ‘분’으로 표시한다. 이 값은 실제 정류소 통과를 관측해 계산한 운행 간격이 아니다.

예를 들어 5511의 유회진학술정보관.제1공학관 정류소(120000174, 순번 66)는 수집 당시 첫 버스가 10분56초 후, 두 번째가 20분54초 후로 예측됐다. 두 도착예정의 차이는 `1254 - 656 = 598초`, 즉 **9분58초**다. 이는 현재 예측된 도착 간격이며, 실제 통과 간격은 지속 관측 후 별도로 계산해야 한다.

경로 추천에서는 사용자가 정류소까지 걷는 시간을 고려한 뒤 탈 수 있는 도착예정 버스를 고르는 것이 필요하다. 배차간격 7분을 곧바로 현재 대기시간 7분으로 사용하면 앞차를 놓치거나 도착예정의 변동을 반영하지 못한다.

## 정합성 확인과 자료

- [위치 CSV](vehicles.csv), [위치 JSON](vehicles.json): 43건, 고유 노선·차량 ID도 43개다. 경위도 43쌍 모두 숫자이며 경위도 유효 범위 안이다. 교내 경계 필터는 적용하지 않았다.
- 위치 데이터 제공시각은 수집시각보다 **14.6~183.6초 이전**이었다. 최근 수신 위치로 표시하고, 오래된 위치는 지도에서 구분해야 한다.
- [5개 노선 통합 요약 CSV](service_overview.csv): 등록 배차간격, 차량 수, 명시한 정류소의 첫 번째·두 번째 도착예정, 예측 도착 간격을 담았다.
- [도착예정 CSV](../public_arrivals_20261104_165101_356971/arrivals.csv): 노선마다 명시한 정류소 한 곳씩, 도착예정 슬롯 10건을 받았다. 전 정류소의 도착예정을 수집한 자료가 아니다.
- [위치 수집 기록](manifest.json), [도착예정 수집 기록](../public_arrivals_20261104_165101_356971/manifest.json): 요청 조건·출처·수집시각·응답 상태.
- 마을버스 13대의 위치 API 혼잡도는 모두 0(정보 없음)이었다. GPS가 있다고 혼잡도까지 제공되는 것은 아니다.

이번 조회는 한 차례만 수행했다. 주기적 갱신은 구현 전이며, 현재 승인 화면에 표시된 일일 호출량을 고려해 갱신 주기·캐시·노선별 공유 수집을 설계해야 한다.
