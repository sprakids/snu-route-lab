# 기존 v7 전 정류장의 20분 초과 연속대기

2026-11-10. `gate_access_calibration_2026-11-09/candidates/alpha_075`의 저장된 peak 월~금 audit를 읽었습니다. 새 시뮬레이션·모델 수정·배포는 없습니다.

## 집계 기준

- 연속대기는 동일 정류소의 인접한 대기 구간을 합칩니다. 같은 자리에서 노선만 바꿔 대기 기록이 나뉘어도 시간이 초기화되지 않습니다. 도보 또는 승차 구간이 끼면 새로운 대기입니다.
- 준비시간 20초를 포함한 물리적 정류소 체류이며, 1,200초 **초과**가 대상입니다. 수치 비교 허용오차는 1e-6초입니다.
- 23:10 미탑승 종료는 우측 검열한 값이며, 지도용 +1초 표시를 제외했습니다. 따라서 진짜 최종 대기는 더 길 수 있습니다.
- 아래 주 표는 20분을 넘긴 노출의 일부가 11:20~23:10과 겹친 경우입니다. 11:20에 이미 기다리고 있던 사람의 경과시간을 초기화하지 않습니다. 저장된 전체 시간대의 별도 결과도 CSV/JSON의 `all_saved`에 있습니다.
- 모두 가중 이동 사건량입니다. 개별 학생 실측 수나 독립 표본 수가 아닙니다.

대기사건량은 같은 이동이 두 정류소에서 긴 대기를 하면 두 번 셉니다. ‘한 번 이상 겪은 이동량’은 최종 가중 이동 분기별로 한 번만 셉니다. 비율의 분모는 해당 요일의 전체 최초 계획 이동량이며 11:20~23:10 출발만으로 분모를 제한한 값이 아닙니다.

‘모형 입자·정류소 방문 수’는 `(원래 합성 입자 ID, 정류소, 연속대기 시작 시각)`의 수입니다. 사람 수가 아니며, 입자 분해 방식에 따라 달라집니다. 최종 분할 레코드 행 수는 검증용으로 CSV에 별도 보존했고 인원으로 제시하지 않았습니다.

월요일 최장 사례는 서울대정문 21299, 화요일은 관악사삼거리 21279, 수·목·금은 국제대학원 21285입니다. 특정 두 정류소만의 문제로 제한할 수 없습니다.

같은 정류소 노선 변경으로 두 개 이상 대기 기록을 합쳐야 하는 긴 대기사건량은 월 367.646, 화 357.451, 수 338.743, 목 156.508, 금 4.147명 상당·회입니다. 이는 원시 대기 행을 개별로 검사하면 연속대기 판정이 달라질 수 있음을 보여줍니다. 이 수치가 전부 누락됐다는 뜻은 아닙니다.

## 검증과 재현

`python -X utf8 shuttle_analysis/continuous_wait_audit_2026-11-10/analyze_continuous_waits.py`

시뮬레이터를 import하지 않습니다. 최종 분할 이동의 가중치를 보존해 합산했으며, 요일별 최초·최종 이동량, 원시 대기 구간 가중량과 wait_audit 가중량, 정류소별·전체 대기사건량을 각각 1e-5 이내로 대조했습니다. prepared와 5개 audit의 분석 전후 SHA-256도 일치합니다.

- `weekday_summary.csv`: 전체 저장 시간대와 표시 시간대의 요일별 두 집계.
- `by_stop_weekday.csv`: 전 정류소의 요일별 상세값.
- `analysis.json`: 정의·분모·원본 해시·검증 결과.
- `run.txt`: 성공한 읽기 전용 실행 로그.

새 후보가 20분에 강제로 사람을 걷게 하면 이 지표는 구조적으로 줄어듭니다. 그 결과를 자발적 행동 모형의 정확도나 현장 검증 성공으로 해석해서는 안 됩니다. 강제 개입 전 이상 사례와 개입 후 결과를 따로 비교해야 합니다.
