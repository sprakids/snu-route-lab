# v7 복원 경로의 읽기 검토

## 최종 운영 복원 검증 완료

실험실 담당자가 단일 개선 후보의 `REJECTED_REVERT_TO_V7` 판정 후 시뮬레이션 배포 `dpl_9z9SDQ4f1cRbBe7zHH5VBPhppBBi`를 운영 승격했다. 앱 코드는 0.22.1을 유지하며, 2026-11-10 01:10 KST에 공개 주소에서 복원 발행 `261110005327` 수용과 v8 운행시계 비활성화를 확인했다. 발행 ID·시각을 제외한 계산 내용은 원래 v7 `261109173153`과 동일하다.

공개 경로 계산의 40개 후보는 동일 복원 모델을 사용하고 시간합계가 일치했다. 기본 뷰어는 capacity_v7이며 v7 common은 원본 Brotli 바이트와 일치한다. 기존 설명서 2개와 [복원 원인·시험 보고서](https://snu-shuttle-simulation.vercel.app/rollback-report.html)는 HTTP 200이다. 과거 v8 원문은 원래 SHA를 유지한 채 공개 접근 가능하고 v8 common도 HTTP 200으로 보존돼 있다. 앱 소스 72개는 변경하지 않았다.

최종 근거: `public_verification/receipt.json` 및 개별 HTTP 응답. 아래 읽기 검토·초안·오프라인 staging 기록은 모두 이전 단계의 증거로 보존했다.

현재 앱 0.22.1과 운영 모델 v8의 롤백 수용 여부만 검토했다. 앱 소스·운영 배포·공개 latest·별칭은 변경하지 않았다. 실험실 담당자의 정문 운행시계 후보 1회 시험도 이 작업에서 실행하지 않았다.

## 결론

v7의 과거 배포를 그대로 재승격하는 것만으로는 앱이 일관되게 복원되지 않는다. `queue_model_sync.py`는 현재 모델보다 작은 발행 ID를 `older_release`로 거부한다.

| 현재 서버 상태 | latest가 과거 v7 ID 261109173153일 때 |
|---|---|
| 이미 v8 261110002926을 읽은 인스턴스 | 과거 ID를 거부하고 v8 유지 |
| 로컬 기본 모델에서 시작한 새 인스턴스 | 기본 모델보다 새 ID인 v7을 받아들임 |

따라서 단순 별칭 복원은 인스턴스에 따라 모델이 달라질 수 있다. 앱 코드를 바꾸지 않는 최소 대안은 **계산 내용이 동일한 v7을 실제 복원 시각의 더 큰 발행 ID로 다시 발행**하는 것이다. 시간 ID는 새 버전의 정확도나 개선을 뜻하지 않으며 이번 경우에는 복원 발행을 뜻한다.

## 로컬에서 검증한 최소안

- 원본 v7 ID: `261109173153`
- 원본 v7 본문 SHA-256: `e9dde3d712ff208f9bfe8a41c79de04da7e1cfc430ca549845182ee97f254865`
- 원본과 동일한 계산 내용 해시: `57cc1bc6822b804598155fe91b78f59cd591cb6e0c0e2341366c3255409a4d06`
- 로컬 초안 ID: `261110005327`
- 초안 본문 SHA-256: `6e5a1e6fbf879b0e7552f57745b47f2f38fc8d3f0834de9c101cb4050c729031`
- 초안 위치: `drafts/261110005327/routing-model/`

초안은 `model.id`, `release.model_id`, `release.published_at`만 변경했다. 수요·정원·FIFO 곡선·시계·계수·기존 출처 정보는 원본 v7과 같다. 전체 JSON 객체에서 이 세 발행값을 원래대로 돌리면 원본 객체와 완전히 같고, 계산 내용 및 호환성 해시도 같다. 발행값이 달라졌으므로 전체 본문 바이트 해시는 달라진다.

실제 앱 reader를 네트워크 대신 고정 응답으로 실행해 다음을 확인했다.

1. 이미 v8을 읽은 인스턴스가 과거 v7 ID를 거부한다.
2. 새 인스턴스는 과거 v7 ID를 받아들인다.
3. 새 ID의 v7 내용은 이미 v8을 읽은 인스턴스에서도 받아들인다.
4. 수용 후 `city_operations.available=false`가 되어 v8 시계를 더 사용하지 않는다.
5. 진행 중인 경로 계산은 기존 모델로 고정되며, 다음 계산부터 복원 모델을 사용한다.

실제 초안 파일 자체도 reader 수용을 확인했다. 검증 기록은 `verification.json`, `draft-verification.json`이다. 앱 소스 72개 파일의 SHA-256 불변을 확인했다. 공급자 호출과 전체 capacity 시뮬레이션 실행은 모두 0회다.

## 복원이 결정됐을 때의 적용 순서

1. 실험실 담당자가 후보의 통과/실패를 판정한다. 이 검토는 그 판정을 대신하지 않는다.
2. 당시 운영 가능한 모든 모델 ID를 확인한다. 초안보다 새 모델이 이미 배포됐다면 초안을 그대로 쓰지 않는다. `python prepare_v7_overlay.py --active-id <당시 가장 큰 ID>`로 현재 KST 시각의 새 초안을 만든다. 이 도구는 더 작은 ID 생성을 거부한다.
3. 보존된 v7 뷰어·데이터의 검증용 새 배포를 만들고, 위 `routing-model/latest.json`과 대응 `releases/<새ID>.json`을 마지막에 덮어씌운다. 과거 Vercel 배포는 불변이므로 과거 배포에 새 파일을 추가할 수는 없다.
4. 기본 데이터셋과 향후 발행 선택도 v7로 유지한다. 일반 publisher가 새 overlay를 v8로 다시 덮어쓰거나 v7을 재계산한 다른 본문으로 바꾸지 않도록 한다. 원본 내용 보존을 위해 이 최소안은 기존 v7 JSON을 직접 재포장하며 재보정·재집계하지 않는다.
5. 검증용 배포의 기본 뷰어, latest/본문 ID·해시·내용 해시, 앱 reader 수용을 확인한 다음 해당 배포를 승격한다.
6. 앱은 요청 시 최대 60초 간격으로 발행을 확인하므로 다음 확인 이후의 모델 ID·SHA와 v8 시계 비활성화를 공개 주소에서 확인한다. 진행 중인 한 경로 비교는 모델을 섞지 않는다.

이 읽기 검토를 작성한 단계에서는 위 배포·승격을 실행하지 않고 검토와 로컬 초안만 전달했다. 이후 실험실 담당자가 복원을 결정·승격했고, 최상단에 최종 공개 검증 결과를 별도로 기록했다.

## 오프라인 롤백 staging 준비 완료

후속 요청에 따라 2026-11-10 00:59 KST에 기존 `deployment/realtime_autoplay_261109175408`을 새 `deployment/rollback_v7_261110005327_staging`으로 복사했다. 공개 배포·별칭·공개 소스 latest·queue_source·앱 코드는 그대로 유지했다.

- 원본: 110개 파일, 76,146,069바이트
- staging: 111개 파일, 77,733,318바이트
- 기존 109개 파일: 전부 SHA-256 동일
- 교체: `public/routing-model/latest.json` 한 개
- 추가: `public/routing-model/releases/261110005327.json` 한 개
- 제거 파일: 없음
- 기본 뷰어 데이터셋: `capacity_v7`, v8 데이터셋 없음
- 대상 프로젝트: `snu-shuttle-simulation`의 기존 project/org ID 그대로 유지
- 빌드·설치 명령: 빈 값 그대로. 이 staging 배포는 일반 publisher를 실행해 overlay를 덮어쓰지 않는다.

원본 스냅샷 110개 파일을 다시 해시해 보존을 확인했고, 당시 공개 소스 latest와 queue_source 및 앱 소스 72개 파일도 불변을 확인했다. 근거는 `offline-source-snapshot-files.json`, `offline-staging-files.json`, `offline-staging-receipt.json`이다. 이 단계에서는 실제 배포와 승격을 실행하지 않았다. 최종 복원은 담당자가 과거 v8 자료도 함께 보존한 `with_history` 배포로 수행했다.
